# image-maker

HTML/CSS で画像を組み、Playwright で PNG にする。デザインは言葉で詰めるより、並べて見て選ぶほうが早く決まる。だから「8 案を見せる → 選んでもらう → 8 案を作り直す」を確定までくり返す。

サイズや文字を置けない範囲（セーフエリア）は投稿先によって違い、各サービスの仕様も変わる。だからこの Skill には特定の媒体の数値を書かない。投稿先をユーザーに聞き、その時点の仕様を確かめて `spec.json` に書く。

## 流れ

1. 聞き取り（ブリーフ）
2. 載せる文章を決める（`texts.json`）
3. 作業フォルダを作る
4. 1 回目: 方向性を大きく変えた 8 案
5. 見せて、選んでもらう（何が良かったか・何が違ったかも聞く）
6. 2 回目以降: 良かった点は残し、まだ決まっていない観点を変えた 8 案
7. 確定したら仕上げて書き出す

## 1. 聞き取り

足りないものだけを、まとめて 1 回で聞く。

| 項目 | 例 | 足りないとき |
| --- | --- | --- |
| 用途・見る人 | 新商品の告知、フォロワー向け | 聞く |
| 載せる文字 | 見出し、補足、日付、価格 | 聞く。詳しくは手順 2 で詰める |
| 素材 | 写真、ロゴのファイル | 聞く。なければ「写真なし」で作る |
| 投稿先・サイズ | Instagram の縦長 1080×1350 | 聞く。ユーザーがサイズを知らなければ、投稿先の現在の推奨サイズとセーフエリアを調べて提案する |
| 雰囲気・決まりごと | ブランドの色、使わない色 | 聞く。「おまかせ」も可 |

写真がないときに、ネットの画像や生成画像で埋めない（権利がわからないため）。代わりに「写真」と書いた枠を置き、あとで差し替えられるようにする。

## 2. 載せる文章を決める

デザインに入る前に、載せる文章をテキストごとに決めて `texts.json` に書く。決めるのは次の 3 つ。

- **何を載せるか**（文章そのもの）
- **表示の都合で変えてよいか**（そのまま／削るだけ可／言い換え可）
- **どれから見てほしいか**（優先順位）

先に決めるのは、案ごとに文章が勝手に変わるのを防ぐため。日付が変わったり店名が言い換えられたりした案は、どれだけ見た目が良くても使えない。決めておけば、変換スクリプトが全案を `texts.json` と突き合わせて機械的に確かめられる。

### 決め方

1. 聞き取った内容から、載せるテキストを 1 つずつ書き出す。
2. それぞれに、変えてよいかと優先順位を仮に付ける。目安:

   | テキストの種類 | 変えてよいか | 理由 |
   | --- | --- | --- |
   | 日付・価格・数値・店名・商品名・電話番号・URL | `fixed`（そのまま） | 1 文字違うだけで誤りになる |
   | 案内・補足（「詳しくはプロフィールのリンクから」など） | `shorten`（削るだけ可） | 狭い配置では縮めたいが、意味は変えたくない |
   | キャッチコピー・見出し | `rephrase`（言い換え可） | 言葉の切り口も案の違いになる |

3. ユーザーに表で見せて確かめる。特に次の 2 点は、ユーザーが決めることなので必ず聞く。
   - 「いちばん最初に見てほしいのはどれですか？」
   - 「削ったり言い換えたりしてはいけないものはありますか？」

優先順位 1 は 1〜2 個にする。全部が 1 だと、どれも目立たない。ユーザーが「全部大事」と言うときは、「スマホで一瞬だけ見た人に、1 つだけ伝わるとしたらどれですか」と聞く。

**事実は作らない。** 価格・日付・数値・産地・受賞歴など、確かめられる事柄は、ユーザーから受け取ったものだけを `texts.json` に入れる。キャッチコピーの言い回しは提案してよいが、事実を足さない。`texts.json` にない文字が画像に載ると、変換スクリプトが `text-untracked` として知らせる。

### texts.json

```json
{
  "texts": [
    { "id": "headline", "text": "焼きたてを、朝いちばんに。", "priority": 1, "edit": "rephrase" },
    { "id": "date",     "text": "発売日 ◯月◯日",             "priority": 2, "edit": "fixed" },
    { "id": "cta",      "text": "詳しくはプロフィールのリンクから", "priority": 3, "edit": "shorten" },
    { "id": "name",     "text": "（店名）",                   "priority": 3, "edit": "fixed" },
    { "id": "status",   "text": "数量限定",                   "priority": 4, "edit": "fixed", "optional": true }
  ]
}
```

| 項目 | 意味 |
| --- | --- |
| `id` | HTML の `data-text` で参照する名前（英数字） |
| `text` | 載せる文章。改行と空白は比べるときに無視されるので、改行位置はデザイン側で決めてよい |
| `priority` | 視線を集める順番。1 が最初に目に入るもの。同じ数字も可 |
| `edit` | `fixed`: 一字一句そのまま／`shorten`: 文字を削るのは可、足す・変える・並べ替えるのは不可／`rephrase`: 意味が同じなら言い換え可 |
| `optional` | `true` なら載せなくてもよい。省略すると必須 |

### 途中で文章が変わったとき

案を選ぶなかで「この言葉がいい」「日付を入れたい」と言われたら、先に `texts.json` を直してから HTML を直す。言い換えた見出しが気に入られたら、その言葉に書き換えて `fixed` にする。以降の案で、気に入られた言葉が勝手に変わらないようにするため。

## 3. 作業フォルダ

特に指定がなければ、作業ディレクトリの下に作る。

```
image-work/<YYYYMMDD>-<短い名前>/
  brief.md      聞き取った内容と、各回のフィードバック（ユーザーの言葉のまま）
  texts.json    載せる文章（手順 2）
  spec.json     サイズなど。下の「spec.json」を参照
  assets/       写真・ロゴ（ユーザーから受け取ったもの）
  round-1/      1.html … 8.html、notes.md（各案のねらい 1 行）
  round-2/
  final/
```

毎回の HTML を残すのは、「1 回目の 4 に戻したい」と言われたときに戻れるようにするため。

### spec.json

```json
{
  "width": 1080,
  "height": 1350,
  "safe": { "top": 60, "right": 60, "bottom": 60, "left": 60 },
  "minFontPx": 28,
  "previewWidth": 300,
  "background": "#ffffff"
}
```

- `width` / `height`（必須）: 書き出すピクセル数。
- `safe`: 文字を置いてはいけない端の幅。媒体の UI が重なる範囲。背景や写真ははみ出してよい。
- `minFontPx`: これより小さい文字を警告する。スマホで縮小表示されても読める大きさ。
- `previewWidth`: 一覧画像での 1 案の幅。実際に見られる大きさに近づける（フィードで流れてくる大きさで判断してもらうため）。

## 4. 1 回目: 方向性を大きく変えた 8 案

1 回目の目的は、ユーザーが好きな方向を見つけること。似た案を 8 つ並べても選ぶ意味がない。次の観点を組み合わせ、8 案がそれぞれ違う方向になるようにする。詳しい引き出しは `references/design-tips.md`。

- 配置: 中央・左右分割・写真全面・文字だけ・斜め・帯・枠
- 書体: ゴシック・明朝・丸ゴシック・手書き風・太さの差
- 色: ブランド色・反対色・モノトーン・暗い背景・淡い背景
- 言葉: 見出しの切り口（効果・季節・人・数字・問いかけ）。`rephrase` のテキストだけが対象
- 見せ方: 優先順位 1 のテキストを目立たせる方法（大きさ・色・位置・余白）。優先順位そのものは変えない

`round-1/notes.md` に、各案のねらいを 1 行ずつ書く（例: `3: 写真全面＋下に白帯、明朝で上品に`）。

### HTML の書き方

- 1 案 1 ファイル。`<html lang="ja">` にする（ないと日本語の改行や字形がおかしくなる）。`html, body` を spec の幅と高さに固定し、`overflow: hidden` にする。
- フォントは Google Fonts を `<link>` で読み込み、`display=block` を付ける。`swap` だと、読み込み前の代わりのフォントのまま撮影されることがある。ローカルにある日本語フォントは環境によって違うので頼らない。
- 写真は `assets/` を相対パスで参照する。
- `texts.json` のテキストを入れた要素には `data-text="<id>"` を付ける（例: `<p data-text="date">受付開始 <b>◯月◯日</b></p>`）。1 つのテキストを複数の要素に分けるときは、それぞれに同じ `id` を付ける。「写真」と書いた仮の枠のように、文章ではない文字には `data-placeholder` を付ける。
- `rephrase` で言い換えたときは、`notes.md` にその案の言葉を書いておく。
- 見出しの改行は `<br>` で自分で決める。または `word-break: auto-phrase` を使う。日本語は意味の途中で改行されやすい（例:「ぎゅっ／と。」）。
  - `<br>` を入れたら、各行をそれだけで読んで意味のまとまりになっているか確かめる。「はじめ／ました。」「はじま／りました。」は ×、「新作、／はじまりました。」は ○。
  - 1 行が幅に収まらないときは、改行位置をずらしてごまかさず、文字を小さくするか言葉を短くする。
- 文字を置けない範囲（safe）の中に、文字が入らないようにする。あえて端に置く飾り文字には `data-outside-safe-ok` を、小さくてよい注記には `data-small-ok` を付ける。

### 画像にしてチェックする

```bash
node <この Skill のパス>/scripts/render.mjs --spec image-work/<名前>/spec.json --in image-work/<名前>/round-1
```

`round-1/png/` に各案の PNG と `report.json` ができ、`round-1/sheet.png` に 8 案を番号付きで並べた一覧ができる。

スクリプトが自動で見つけるもの:

- `clipped`: 枠に収まらず文字が切れている
- `off-canvas`: 文字が画像の外にはみ出している
- `outside-safe-area`: 文字を置けない範囲に文字がある
- `small-text`: 文字が `minFontPx` より小さい
- `font-not-loaded`: 指定したフォントが読み込まれず、別のフォントになっている
- `image-missing`: 写真が読み込めていない
- `missing-lang`: 日本語があるのに `lang="ja"` がない
- `text-missing`: 必須のテキストが載っていない
- `text-changed`: `fixed` のテキストが一字一句同じでない
- `text-reworded`: `shorten` のテキストが、削る以外の変え方をされている
- `priority-inverted`: 優先順位の低いテキストのほうが文字が大きい。視線は色や位置でも動くので、大きさ以外で優先順位を表しているなら問題ない。目で見て確かめる
- `text-untracked`: `texts.json` にない文字が載っている。事実を足していないか確かめ、必要なら `texts.json` に加える（ユーザーに確かめてから）
- `text-unknown-id`: `data-text` の `id` が `texts.json` にない
- `auto-wrap`: 大きな見出しが、自分で入れた改行以外の場所で折り返されている（「はじま／りました」のような改行になりやすい）。改行位置を直すか、文字を小さくする。わざと自動の折り返しに任せる場合は `data-wrap-ok` を付ける

見せる前に、見つかった問題は直して撮り直す。壊れた案は、ユーザーの選ぶ手間を無駄にするため。

そのあと、`sheet.png` を自分で開いて目で確かめる。自動では見つけられない次の点を見る:

- 不自然な改行、行頭の句読点
- 背景と文字の色が近くて読みにくい
- 縮小した大きさで、優先順位 1 のテキストが最初に目に入るか
- 8 案が十分に違っているか（1 回目）

## 5. 見せて、選んでもらう

`sheet.png` を見せる（ファイルを送る道具があれば画像として送る。なければパスを伝える）。続けて、各案のねらいを 1 行ずつ添え、次のように聞く。

> 気になる案の番号と、**その案の何が良かったか**を教えてください（色・配置・書体・写真の扱い・言葉・雰囲気など、ひとことで大丈夫です）。
> 選ばなかった案で「これは違う」と思ったものがあれば、それも教えてください。
> 「2-3 の配置で、色は 1-5」のような組み合わせも大丈夫です。決まったら「2-3 で決定」と言ってください。

理由まで聞くのは、次の回のバリエーションを広げるため。「何が良かったか」がわかれば、そこを残したまま、それ以外を大胆に変えられる。理由がわからないと、選ばれた案を丸ごと残して細部だけを変えるしかなく、似た案が 8 つ並ぶ（試運転で、3 回目に「もうここから大差ない」と言われた）。

### 理由のない返事だったとき

「2-7 いいね」のように番号だけの返事なら、作り直す前に 1 回だけ短く聞き返す。答えやすいように、その案の特徴を選択肢にして示す。

> 2-7 の良かったところはどれですか？（いくつでも）
> ① 暖色の背景　② 丸い写真と白い枠の配置　③ 明朝体の上品さ　④ 「焼きたてを、朝いちばんに。」の言葉　⑤ 全体の雰囲気

聞き返すのは 1 回だけにする。それでも理由が出てこなければ、ユーザーも言葉にしにくいということなので、推測で進め、推測した内容を次の一覧に添える（例:「色と配置が良かったと受け取り、書体と言葉を変えてみました」）。

### 記録

案は必ず「回-番号」（`1-1`〜`1-8`、`2-1`〜`2-8`）で呼ぶ。どの回の案かを取り違えないようにするため。

ユーザーの返事は、`brief.md` にそのまま書き写す。言い換えると、意図がずれていくため。そのうえで、ここまでにわかったことを次の 3 つに分けて書き足していく。

```
- 残す: 暖色の背景（2-7）、丸い写真（1-4, 2-7）
- 避ける: ポップな書体（1-6 は違う）
- まだわからない: 見出しの言葉、書体
```

## 6. 2 回目以降: 磨いた 8 案

選ばれた案の HTML をコピーして土台にする。ゼロから書き直すと、気に入られた細部が消えるため。

`brief.md` の 3 つの分類を使う。

- **残す**ものは変えない。
- **避ける**ものは使わない。
- **まだわからない**観点を変える。ここがバリエーションの出どころになる。

8 案の内訳:

- **5〜6 案**: 「まだわからない」観点を 1 案ごとに 1 つずつ、はっきり変える（例: 書体を明朝 → 丸ゴシック、言葉の切り口を季節 → 作り手）。縮小した一覧で違いがわかる量にする（見出しなら 1.2 倍以上、色ならはっきり違う色）。1 案で変えるのが 1 つの観点なら、次の選択から「何が効いたか」がわかる。
- **2〜3 案**: 少し外した案。「残す」の一部をあえて崩す案もここに入れてよい。全部を寄せると、もっと良い方向を見逃すことがある。

`notes.md` には、各案が前のどの案から何を変えたかを書く（例: `4: 2-3 を土台に、書体を丸ゴシックに`）。

画像にしてチェックし、見せる、を 4・5 と同じ手順でくり返す。

### 8 案を作らなくてよいとき

- 「まだわからない」観点がほとんど残っていない（ほぼ決まっている）なら、8 案を作る前に「この案で決定にしますか、もう少し磨きますか」と聞く。作り直しの 1 回分を省ける。
- フィードバックが 1 案への細かい修正だけ（「この文字をもう少し右に」など）のときは、修正版を 1 案見せ、確定してよいか聞く。

### 決まらないとき

3 回くり返しても方向が定まらないときは、8 案を出し続けずに、`brief.md` の 3 つの分類を見せて「この理解で合っていますか」と確かめる。どこかで受け取り違えている可能性が高いため。

## 7. 仕上げ

1. 確定した案の HTML を `final/final.html` にコピーする。
2. spec の大きさで書き出す:
   ```bash
   node <この Skill のパス>/scripts/render.mjs --spec image-work/<名前>/spec.json --in image-work/<名前>/final/final.html
   ```
   投稿先が決めているピクセル数のまま書き出すのが基本。ユーザーが高解像度を望むときだけ `--scale 2` を付ける。
3. `report.json` の問題が 0 件であることを確かめ、PNG を原寸で開いて確認する。
4. PNG をユーザーに渡す。あわせて、あとで文字や日付を差し替えられるように `final.html` の場所を伝える。
